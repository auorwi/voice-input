# 清爽与结构化

本个人版只提供两种普通听写风格。此设置改变发给 LLM 的 system 提示词，不切换模型、不调用第二个模型，也不在模型输出后机械插入编号。

## 代码链路

```mermaid
flowchart LR
  A[设置选择并保存 polish_style] --> B[AppConfig 加载及兼容归一化]
  B --> C[语音转写文本和当前应用场景]
  C --> D[pipeline 构造 PolishRequest]
  D --> E[build_context_system_prompt]
  E --> F[DeepSeek OpenAI 兼容接口]
  F --> G[保留换行的文字结果]
  G --> H[写入当前输入框或结果弹窗]
```

- `src/components/Settings/LlmPane.tsx`：两项选择和解释文字。点击保存后配置进入后端。
- `src/stores/appStore.ts`：`PolishStyle` 只允许 `clean`、`structured`。
- `src-tauri/src/storage/mod.rs`：旧的 `minimal`、`professional` 及未知值归一为 `clean`；已有 `structured` 保留。
- `src-tauri/src/pipeline.rs`：把保存的风格、转写、上下文和场景传入 `PolishRequest`。
- `src-tauri/src/llm/prompt.rs`：组装完整 system 提示词。当前版本为 `voice-input-styles-v4`（应用 1.1.63）。
- `src-tauri/src/llm/openai.rs`：发送 system 提示词及 `<transcription>` 中的原文。DeepSeek 走这条兼容接口路径。

## 风格与优先级

| 风格 | 输出约定 |
|---|---|
| 清爽 | 去无意义口头词和偶然重复、修顺语句；自然短句和段落，不自动加标题或列表，不丢信息 |
| 结构化 | 保留完整表达与原有叙述结构；实际列表编号，背景、解释、补充想法和结尾请求保持段落；任务的负责人、期限、条件与后续补充归入同一项 |

通用规则负责事实、否定、主观语气、条件、语言和安全边界；应用和场景负责语气及用词；最后追加所选风格的排版约定。结构化只使用通用规则，不把任何测试案例或输出模板写入提示词。场景存在时不再跳过风格。选中文本或显式语音操作保留自身的转换要求，不套用普通听写排版。

语言和翻译行为保持原样：结构化不强制中文或英文。普通听写沿用原语言，“始终翻译输出”和翻译操作仍遵循目标语言。

## v4：语义边界与精确表达

1.1.63 延续完整表达目标，并使用不含具体示例的通用规则：

- 时间、数量、单位和限定整体保留，区分完整时段、截止边界、每项分配与总量；数字换写法不能改变范围。
- 保留关键名词、人名与技术标识，不猜补转写没有提供的时段、分配方式或事实。
- 先确定列表边界。共同安排通常在任务列表外；明确枚举或独立指派的安排仍保留为一项，不能机械地把涉及时间的内容都移出列表。
- 收齐全部并列任务及后补细节，首个任务不是前言；问句依据语义恢复问号，随后的解释单独成句。
- 英语和中英混合输入仍沿用其语言，自动翻译与显式操作逻辑没有变化，Clean 提示词未变。

本轮先隔离 LLM 层，用固定虚构输入作新旧对照。对用户播客测试的一条匹配本地记录作只读核对后，发现若干与朗读原稿的差异在 `raw_text` 中就已存在，不能归因为润色删除；没有原始音频，不能进一步区分朗读差异与识别错误。此版本不声称修复这些上游偏差，也不在提示词中猜回原稿。该历史文本不加入公开测试 fixture。

本轮扩充的测试覆盖播客、展品寄送、精确图像记录、英文共同条件、明确枚举的共同要求、无明确时段/分配范围的输入和缺问号的转写形态；例子仅在测试文件里，生产提示词不读取它们。自动筛查与人工语义、排版核对分别记录，不以提示词包含某个英文短语作为输出质量证明。

最终冻结规则的二十二组请求全部正常结束。自动筛查为 21/22，人工结构检查为 19/22；未发现有效内容、关键限定、纠错或语言保留失败。三组排版限制分别为：隐式两任务的任务与细节分离、三个任务中的首任务未编号，以及播客任务编号后将各自细节放在列表外。共同发布时间与条件已独立成段，但任务细节的归组仍不稳定。

旧版在完整固定原文上也保留了被检查的精确限定，因此这轮不能被描述为“已修复真实识别漏词”，也未证明整体输出质量稳定优于旧版。最终实测、各轮差异及限制见本轮“结构化迭代实测”报告。当前交付保留这部分已知排版限制，不依靠案例专用规则追求单次测试全绿。

## v3 历史：完整表达与自然结构

用户提供的同段朗读对比显示，旧版把“背景 → 两处修改 → 条件 → 暂定想法 → 请求”全部变成七个带标签的条目；其中一份实际输出还把海报负责人的期限放到预算项下，并改写了结尾的请求语气。

代码中的 `outline` 定位、“两个以上独立事项就编号”和给每项加主题标签的要求，会鼓励这种过度切分。固定原文调用旧生产提示词也复现了活动说明被分成七项、连贯观点被拆成六项的情况。

v3 按顺序执行“明确口误清理 → 按关系组织 → 完整句表达 → 保真检查”，不要求模型输出中间分析。约定如下：

- 使用自然段落与真实列表混排。说“有两处修改”时，只对那两处修改编号。
- 保留每个有意义的分句、例子、理由、补充说明和保留意见；一项可包含多句话，不设置一行一句或摘要长度目标。
- 先说任务、后补充细节时，把负责人、动作、期限、原因和例子正确合并；独立的全局条件保持段落，某项任务的专属条件留在该项。
- 保留“我觉得”“也不一定对”“先不要”和“能不能……？”的立场、限定与请求语气。
- 应用场景中的简洁要求只能清理口头赘词，不能删减内容或强迫整段变成清单。
- 不添加逐句主题标签、标题、总结或没说过的事实。
- 提示词不包含具体输入/输出案例、人物、日期、金额或行业模板。样例仅用于测试，生产提示词不读取这些 fixture。
- 明确区分说话者撤回自身口误与指出现有材料错误：前者保留最终表述，后者保留错误值、正确值和关联对象。

目标参考了用户提供的 Typeless 输出形态；并非取得或复刻其内部提示词。其公开的 [听写说明](https://www.typeless.com/help/quickstart/dictate) 描述了保留意图、处理补充与口头修正的体验，[个性化说明](https://www.typeless.com/help/quickstart/personalization) 则说明其措辞会随使用习惯调整。本次没有新增学习个人习惯的功能。

### v3 真实模型回归

使用 `src-tauri/tests/fixtures/structured_fidelity.json` 中的固定虚构原文，经生产 Rust 提示词函数构建请求，调用已配置的 DeepSeek。不读取历史记录，测试请求关闭自动翻译（不改本机设置）；temperature 0.3、max_tokens 4096，非流式记录响应。

覆盖十一种固定输入，活动输入另测工作聊天和冲突手动场景，共十三组。验证不只统计编号，还逐项核对 fixture 的 `preserve` 清单与任务归属；字数增长不被当作保真证明。清爽以及 Structured 之前的 operation/language 提示词与 v2 导出逐字比对一致。

最终一轮自动筛查十三组通过：响应正常结束、编号数量符合预期、被检查的关键值保留、明确撤回的错误表述未保留。人工逐项核对未发现有效内容遗漏或错误归属；完整排版符合预期的为十二组。有一组隐式任务仍把负责人和期限留在前言、把对应细节放进列表，信息关联可辨，但未完全合并为两个完整任务项。自动筛查通过不代表人工结构检查全部通过。

活动样本只保留两项修改，背景、预算、条件、暂定想法和礼貌请求保持完整。预算留在列表外，避免把活动的全局预算误认作某个负责人的任务。连贯观点、技术解释、日常消息保持自然段落，操作步骤和方案比较使用实际列表。详细原文、真实输出与人工核对记录保存在本轮交付的“结构化保真实测”报告中。

这是固定文本的 LLM 验证，未重测麦克风、语音识别或自动写入。模型仍可能出现分组或措辞变化，不保证任意输入零遗漏。

更早版本曾有场景跳过内置风格、所有风格都强制列点等问题，已在 v2 解决。v3 沿用这部分逻辑，只调整 Structured 的通用整理规则及界面说明。

## v2 历史验证（2026-09-28）

以下保留上一轮结果，全部独立事项编号的旧约定已由 v3 替代。

测试使用生产 Rust 提示词函数、虚构转写、DeepSeek 已配置端点；请求 `deepseek-chat`，响应字段返回 `deepseek-flash`。temperature 0.3、max_tokens 4096；非流式记录结果，未测试麦克风或桌面输入。

最终一轮 9 组配对、18 次调用：

- 9/9 清爽输出没有自动编号。
- 8/8 多事项结构化输出逐行编号。
- 简单会议通知，两种风格均保持一句话。
- 多事项通用场景重复 3 次；另测邮件、工作聊天和要求单段落的冲突场景，所选风格均生效。
- 检查人物、日期、预算、否定、条件、主观语气以及 `API`、`QA`、`user_id` 等技术标识，均保留固定关键内容。

同一口述的实际输出示例：

清爽：

> API timeout 设成 20 秒，不要改成 30 秒，retry 还是两次。iOS 的登录按钮有重叠，Leo 今天修一下。上线要等 QA 通过，不要动 user_id 这个字段

结构化：

```text
1. API：timeout 设成 20 秒，不要改成 30 秒；retry 还是两次
2. iOS 登录按钮：有重叠，Leo 今天修一下
3. 上线：要等 QA 通过
4. user_id 字段：不要动
```

多事项复测有 4 条或 5 条的分组变化，表明具体组织方式仍由模型判断。固定样本通过不代表所有输入均能完全保真，也不代表语音识别、权限和自动写入的端到端验证。

本次回归还覆盖了场景存在时风格仍被传入、旧配置迁移、界面只有两项，以及显式语音操作不受普通听写格式影响。
